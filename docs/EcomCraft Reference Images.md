## 1. Background and User Story

Besides their own product photo, operators often hold **finished images from competitors**: layouts, scenes, lighting and prop styling worth borrowing. They want "an image with the same feel, but with my product", not a text description of a composition — operators cannot phrase "45-degree overhead, clear space upper-left, warm morning light".

User story: *"I upload my product photo and several reference images (say a competitor's main image, scene image and detail image); the platform generates one image per reference — each matching the feel of its own reference, but with my product."* Later: use a competitor's whole image set as references and generate one's own set in one go.

## 3. The Two Paths

### 3.1 Path 1: borrow the composition (prompt reference)

Each reference image goes to a vision model (MagicPrompt's vision capability; on by default per decision A5, administrators can turn it off), which produces **that reference's own** English composition description (camera, light, scene, color); it becomes that reference's prompt, shown to the user for editing (edits win), and the existing text-to-image plus product-preservation pipeline does the rest. In reference mode no product-type, style, model or brand fragments are appended.

- One reference, one task, one description — **never merged, never mixed**, so multiple references cannot fight each other.
- No new generative model is needed; the existing text-to-image pipeline works as is.
- Effect: the broad direction of layout and mood carries over, details less so — consistent with this fallback path's positioning (the former "restore the feel" red line was relaxed per D2 to allow highly similar results; see decision 2 and 3.3).
- With image description off or no usable vision model: reference mode is unavailable and the page says what is missing and how to fix it (F68); plain generation is unaffected.

### 3.2 Path 2: scene reference (image-to-image, P2; superseded by T84's fusion route on 2026-10-31)

The reference image becomes the input of an image-to-image / image-edit workflow: "put my product into a frame with a similar feel".

- **Each task's reference is its own input**: with one-to-one mapping the single-input nature of image-to-image is a perfect fit; multi-image blending (IPAdapter-style) is left for later.
- **Formerly depended on N10**: from 2026-10-31 this is superseded by T84's `reference-edit.json` blueprint and the G1-selected model; N10's model choice folds into the G1 trial. Template `requirements`, the F08 checklist and dependency checks are unchanged.
- **The template declares a `reference` slot** (like the brand kit's F12 `reference_image`): `"reference": { "image": "parameter ID" }` pointing at an image parameter of the workflow snapshot; it may not point at the same parameter as `brand_kit.reference_image` (a validation error). Clients submit only image data; the server fills the parameter per task; the allowlist boundary is unchanged. T84 reuses this design (`Templates/builtin/reference.json`).

### 3.3 Route upgrade: reference fusion (route E, 2026-10-31, pending the G1 trial)

User feedback says the current route (vision prompt → inpaint → paste back) produces poor results: text descriptions cannot preserve exact layout, perspective and lighting; product placement relies on manual estimation; a single fixed-angle product photo rarely matches the scene's camera; and the fusion does not re-light the product for the scene. The new route lets the model directly "see" the reference and the product photo:

1. **Analyze the reference** (T83): automatically derive the subject's position and size (SwarmRemBg mask bounding box), the slot role (main / scene / selling / detail) and flags (has_text, has_person, subject_count); replacing manual placement (T79 stays as a correction).
2. **(Optional) clean up**: remove the old product, text, logos; trials decide whether needed.
3. **Fuse** (T84): reference (or clean scene) + product photo → editing model (candidates: Qwen-Image 2.1, Qwen-Image-Edit-2511, FLUX.2 klein 4B; unmeasured, not a conclusion).
4. **Restore the product** (T86): locate it in the result; paste the original details back when contours align; never force it when they do not (angle changed).
5. **Verify** (T86): retry once on excessive difference; still failing, flag "product may be distorted" — never deliver silently.
6. **Text**: re-laid-out by SellingImageService.

The route, model and quantization follow the G1 conclusion (trial schemes R0–R5 in phase 1 of the [EcomCraft Implementation Plan](EcomCraft%20Implementation%20Plan.md)). Once the new route lands: the generation page becomes the single entry "follow a reference" (A14); the old borrow-the-composition path stays as the `reference_mode: composition` fallback with `reference_strength` offering "borrow composition only / highly similar"; per-reference editable prompts stop being required (`reference_prompts` becomes optional, the server template generates the prompt).

## 4. Interface and Interaction (reference mode)

1. **Reference images (optional) entry**: a new upload entry in step 2, **at most 8**, wrapping rows of thumbnails; a 9th is refused with a hint about the cap. Uploads are compressed client-side (the same 5 MB cap as gallery picks, F52) and validated server-side like any image. Each can be removed.
2. **Uploading enters reference mode**: the step-2 image type, visual style, model checkbox, brand kit, one-line description, candidate count and storyboard are **disabled and marked "not used in reference mode"**; the platform stays selectable (for later export and the international notice).
3. **Per-reference prompts**: right after upload, the vision model describes each reference in the background (list items show "describing...") and several references are described one at a time in a queue (a local vision model reads one image at a time, so sending them all at once made the later ones time out), and waiting ones show "Waiting to be described..."; each description is an English paragraph of 60-120 words covering shot type and camera angle, the product's place in the frame, surface and background, props, lighting, color palette and mood, and photographic style, never the product's type or brand; the description fills that reference's prompt field: **English is editable** (cleaned server-side, edits win), the Chinese translation is read-only; a failed description can be retried per reference. With vision off, reference mode is unavailable with a hint.
4. **Generate by reference**: the button replaces the two generate buttons and expands as products x references with **exactly one image per reference** (the candidate count does not apply); the live count hint disables the button past 20 images in total (F55).
5. **Storyboard mutual exclusion**: selling-point storyboards (F25) and references are mutually exclusive (the storyboard entry is already disabled in reference mode).
6. **Task cards**: reference-driven tasks show the **thumbnail of their reference** on the card, with the task's actual prompt unfoldable (reusing F56's `prompt_used`).
7. **Copyright notice**: fixed under the entry — references are used only to borrow layout and light; use only images you have the right to use (self-shot, licensed or restriction-free), and keep results clearly distinct from the references.
8. **Stronger notice on international platforms**: when the chosen platform's `region` is `global`, an extra notice appears — international platforms review image similarity more strictly; borrow the layout only and make sure results do not resemble the reference before listing.
9. **Place the product per reference**: in reference mode, "Place for reference 1 / 2 / ..." appears above the product placement preview in step 1; choosing one shows that reference (cropped square like the output, semi-transparent) behind the preview, and dragging and "Product size" then change only that reference's placement; references not adjusted keep the product's own placement. A fixed hint reads "Match the product's position and size to the reference." The system does not infer placements automatically (confirmed 2026-10-30). The reference backdrop is shown in the browser only and is not uploaded again.

## 6. Copyright and Compliance Boundary

- **Allowed**: users upload their own references; generating compositions, scenes and lighting highly similar to the reference (revised 2026-10-31, D2; boundary in architecture decision A17).
- **Not built**: competitor-link scraping, competitor image libraries or recommendations; no "replicate competitors" marketing — the UI consistently says "follow a reference".
- **Must do**: text, logos and watermarks never enter the finished image (the system re-lays-out text); references with real models do not keep their faces (first batch: prompt "not supported", T88); the fixed copyright notice plus the stronger international-platform notice (section 4).
- Similarity checks between results and references (warning when too close) belong under F21 automatic candidate filtering; not in this phase.
- Platform export (F58) does not know about references; AI metadata follows the existing F22 rules.

## 7. Storage and Privacy

- References **exist only inside the request and the in-memory batch**: kept in memory like product photos for the batch's lifetime (six hours), **never written under `Data/`**, and never entering the product library (F36), the project archive (F04), the candidate-cleanup registry (F39), diagnostics (F44) or backups (F45).
- Visible only to the submitter; shared queue and progress APIs never return references.
- Implementation adds the matching rule to AGENTS.md (as F04 did).

### 8.1 Vision Model Device (F71)

Customer computers may have NVIDIA, AMD or Intel graphics, be a Mac, or have no discrete graphics at all. Some cards hang on the vision model: an older AMD card such as the RX 5600 XT on Windows is not on the ROCm support list, so Ollama runs it through Vulkan, image requests produce nothing for minutes, and afterwards Ollama reports the model as loaded while it holds no video memory, so even plain text requests hang until the model is unloaded; the same computer finishes an image in about 8-18 seconds on the CPU. Image description must therefore pick its device per machine instead of assuming the graphics card works.

| Phase | Content | Task |
|---|---|---|
| P1 | (1) Turn off thinking for Ollama (works for hybrid Qwen3; measured: the plain Qwen3-VL tags are thinking variants that ignore `think:false`, so the recommendations and the one-click install use the `-instruct` tags, and the settings suggest switching when a thinking variant is installed) and limit image requests to a 4096 context; (2) after an image request times out, ask Ollama to unload that model to clear the hung state, and cancel the underlying request when the wait is given up; (3) in "Automatic" mode, the first image request for each "Ollama address + vision model" waits at most 60 seconds on the GPU; without an answer the model is unloaded and the request retried on the CPU, which is remembered while the service runs (decided again after a restart), and machines whose GPU answers are unaffected; (4) administrators can set the device to "Automatic / GPU only / CPU only" in the prompt enhancement settings, and after an automatic move to the CPU the settings say why and suggest choosing "CPU only" | T75 |
| P2 | Measured self-test (implemented, pending acceptance): on first setup, a model or Ollama version change, or a graphics change, a built-in test image is run with a time limit on the GPU and on the CPU, the device that answers and is faster is chosen, and the timeout is set from the measured speed; the result is saved in the data folder by "Ollama version + model + graphics name + driver version" (device and seconds only), the settings show "Vision: GPU / CPU, about X s per image" with a re-test button, and automatic moves to the CPU are saved too so a restart does not hang again | T76 |
| P3 | Starting device and recommended model from the hardware (hardware is read only when Ollama runs on the same computer as this service): NVIDIA recommends 8B / 4B by video memory; AMD cards on the ROCm support list go by video memory while older models and Intel graphics start on the CPU; Apple Silicon goes by memory; no discrete graphics uses the CPU and 2B. When the card is shared with ComfyUI and has little video memory, image description defaults to the CPU or unloads right after describing, so it does not take memory from generation | T77 |

**P2 implementation (T76):** the self-test runs only in "Automatic" mode: once in the background when the vision status check finds no record for the current combination, and whenever an administrator clicks "Test again" in the settings. The test image is generated by the server and contains no user image; it first waits at most 60 seconds on the GPU, then unloads the model and waits at most 120 seconds on the CPU, and picks the device that answers and is faster; when both fail nothing is saved and it is tried again automatically after the vision settings change or a model is installed; when users describe images during a test (Ollama queues the requests, so the times would be wrong) its result is discarded and the test repeated later, and what those requests learn is not saved either. The result is written to `Data/EcomCraft/vision-device.json` (replaced through a temporary file, never overwritten when it cannot be read), keyed by "Ollama version | model | graphics": when Ollama runs on the same computer as this service, graphics means the local graphics names and driver versions; when it runs on another computer on the LAN its graphics cannot be read, so a one-way digest of the address tells servers apart (the address itself is not saved); at most 20 entries are kept. With a record, "Automatic" uses the recorded device right away instead of waiting 60 seconds on the GPU first, and the wait for an image is 5 times the recorded seconds (at least 90 seconds, never more than the configured timeout). What the first request of a run learns is saved the same way. `EcomCraftPromptSettings` adds `vision_check` (`state` none / running / done / failed, plus `device` and `seconds`); `EcomCraftStudioVisionDeviceCheck` needs the server-settings permission and starts a new test.

No phase changes the rule that references exist only briefly in memory; saved test results hold only the device choice and timings, never images or prompts; the APIs return only the device choice and status, never the Ollama address.

## 9. Acceptance Criteria (T61)

- With 3 references and 1 product: 3 images, each matching **its own** reference's composition (not a blend); a 9th upload is refused with a hint.
- After upload, the image type, visual style, model checkbox, brand kit, one-line description, candidate count and storyboard are disabled and marked; the generate buttons become "generate by reference".
- Each reference's prompt is editable: after editing the English and submitting, the task card's `prompt_used` shows the edited prompt.
- 2 products x 8 references = 16 images submits; more products or references past 20 disables the buttons with a reason; exactly one image per reference.
- Storyboards and references together prompt a choice; with vision off reference mode is unavailable with a reason, and plain generation is unaffected.
- Task cards show their reference thumbnail and actual prompt; references never appear in the product library, gallery, archive or diagnostics; nothing remains after a service restart.
- International platforms show the stronger notice; Chinese platforms show the basic copyright notice only.
- The interface is complete in both languages; the `studio-i18n` and `simple-mode` tests pass.
