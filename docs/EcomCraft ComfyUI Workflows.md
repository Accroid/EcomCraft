# Calling ComfyUI Workflows in EcomCraft

> **Language:** English · [简体中文](EcomCraft%20ComfyUI%20工作流.zh-CN.md)

EcomCraft never exposes arbitrary ComfyUI JSON to ordinary clients. ComfyUI workflows saved on execution servers are discovered automatically and become available to users only after review (see "Review and publishing" below). Administrators can also open an existing workflow in SwarmUI's ComfyUI workflow editor, confirm its dependencies and parameters, enable **Enable in Simple** and save it; such workflows do not go through EcomCraft review.

## Web page

1. Make sure at least one execution server (the local `ComfyUI Self-Starting` backend, or a registered LAN ComfyUI, see "LAN execution servers" below) has the status `RUNNING`.
2. Open EcomCraft Studio. While the page is visible and not generating, the workflow list refreshes every 30 seconds; you can also click "Refresh" next to "Creative workflow" to update it immediately. The catalog also refreshes when an execution server becomes available again.
3. Choose a published workflow in the "Creative workflow" drop-down (an approved native workflow, or a workflow an administrator enabled for the simple workspace in SwarmUI).
4. Fill in the inputs the workflow shows and the standard prompt, then click Generate.

The workflow drop-down shows only workflows that meet all of these conditions: the current account may use them, the workflow has been approved and published (or enabled for the simple workspace in SwarmUI), and its JSON and parameter definitions are valid. If a reviewer hid a model parameter, the current account must also be allowed to use that model. Image and video workflows are listed separately by type.

Besides workflows published by administrators, EcomCraft reuses the local ComfyUI installation discovery to scan `workflows`, `blueprints`, `user/default/workflows` and `user/default/blueprints` in configured backends and other verified local installations. A configured backend's `--user-directory` override still applies. Installation scan results are cached for 60 seconds, so a newly added installation appears at the first catalog refresh after the cache expires; newly saved files in an already discovered installation appear at the next refresh. You do not need to enter file paths one by one; `Settings.EcomCraft.ComfyWorkflowSearchPaths` only adds non-standard directories and does not turn off automatic discovery. Registered LAN execution servers are read through the ComfyUI HTTP API, which lists the workflows saved in their `user/default/workflows`.

Workflow discovery runs in the background and refreshes about every 30 seconds; catalog and API requests never scan synchronously. The first request after the service starts waits at most 5 seconds for the first results. If a source temporarily cannot be read, its previous results are kept.

## Review and publishing

Automatically discovered native workflows are not available to users directly; they must be reviewed first:

1. Discovered workflows enter "Pending review". Accounts with the `ecomcraft_submit_workflows` permission (ordinary users by default) can choose a workflow they saved on the workspace "Workflows" page, add a note and click "Submit for review", and can see its status and any rejection reason.
2. Accounts with the `ecomcraft_review_workflows` permission (administrators by default) open the workflow on the "Workflow review" page, check which servers can run it (for example "Only A (B: missing node xxx)"), decide for each parameter whether it is shown and set its display name, default value, range and drop-down options, then click "Approve and publish", or "Reject" with a reason. Published workflows can be "Unpublished".
3. Approval saves a snapshot, and users run the snapshot. If the source file is later changed in ComfyUI, the status becomes "Needs re-review", and users keep using the old snapshot until the new version is approved. If the source server goes offline or the file is deleted, the published snapshot is unaffected.
4. Workflows that fail structural validation show "Cannot import" with the reason and cannot be submitted or published.

Hidden parameters do not appear in the user form and always use the default value from the snapshot. Creative description, negative content, width and height are always shown. Review records are saved on the server in `Data/EcomCraft/workflow-reviews.json`. Native workflows that were discovered and directly usable before the upgrade must be approved after the upgrade before they reappear in user lists.

Both the old array-style and the new object-style links are supported, as are embedded subgraph blueprints containing positive and negative prompt encoder nodes (for example the Qwen-Image text-to-image blueprint and Qwen 2.1 workflows using `TextEncodeQwenImage21` and `UnetLoaderGGUF`). The positive and negative conditioning outputs of `TextEncodeQwenImage21` are bound to `prompt` and `negative_prompt` respectively; the two text boxes of the same encoder node are not merged. `SaveImageAdvanced` is rewired to the workspace image output so the original author's output path is not reused. A blueprint that has only an image output socket and no save node gets an image output node added on the server; subgraph instances are expanded separately, and connected controls such as steps and CFG keep their connections. Invalid links, cycles, unrecognized prompt inputs, unsupported bypassed nodes and administrator default image inputs are never published as executable workflows. Discovery never sends the raw node graph or internal file paths to clients.

After you choose an automatically discovered native workflow, the page reads the saved positive and negative prompts, size, steps, CFG, seed, sampler and scheduler; model loaders and denoise parameters appear in the workflow input area. Changes are written back to the corresponding nodes according to the server-side bindings, and multiple nodes keep their own independent parameters. Connected known integer/decimal primitive nodes can have their values edited while the connection itself stays unchanged. Catalog refreshes keep unsubmitted changes. The positive and negative prompts are filled with defaults only the first time you enter a native workflow while the text boxes are empty; afterwards, switching models or workflows or returning to the standard workspace keeps the current prompts (including content you cleared on purpose). Choosing a workflow again reads the defaults of the other parameters, and returning to the standard workspace restores the other standard parameters you had before.

In the page connection status, "ComfyUI execution servers" is the number of online execution servers (busy servers count too, since tasks queue for them), and "Standard workspace models" is the number of image/video models in SwarmUI's global list available to the current account. It is not the number of cloud models and does not say whether workflow dependencies are complete.

Native workflows use their model file names directly; SwarmUI's global image model list does not need a model with the same name. The model drop-down lists only models the current account may use and that exist on at least one online execution server. On submission the scheduler checks node and model dependencies server by server; when no server can run the task it returns `no_execution_server` and lists what each server lacks (see "Execution server scheduling" below). The standard workspace and manually published legacy templates still use the original model selection logic; a legacy template with no model available for the current type, or whose model input only offers `(None)`, does not appear in the list.

The seed reads the saved value and supports values up to the JavaScript safe integer limit `9007199254740991`; enter `-1` to randomize on submission. When generating several images at once, the submitted seed is the starting point and increases by 1 per image, synchronized to the actual sampler nodes; other independent seed nodes change by the same increment, continuing from 0 after the limit. With `-1`, a random starting value is chosen first and then incremented per image. The randomize/increment/decrement front-end buttons of the ComfyUI canvas are not executed. The image count is read from the saved batch_size, still limited to 1–4, and each image is scheduled separately by SwarmUI so batch sizes are not multiplied twice.

The generation API normally returns `images`, an array of image URLs. Submitting again with a fixed starting seed and the same parameters reproduces the same set of images and may hit the ComfyUI cache; change the seed or enter `-1` when you want a new set. The system-generated standard workflows default to `-1`, so each generation is a new image; "Make again with the same settings" still uses the original work's seed.

When a local backend is located at `ComfyUI-Installs/<install name>/ComfyUI`, the node pack loaded with SwarmUI automatically adds the sibling `ComfyUI-Shared/models` under the same root to ComfyUI's search paths. Standard subfolders such as checkpoints, VAE, LoRA, text encoders and diffusion models are supported; existing path priorities are kept, models are not copied, user configuration files are not modified, and no custom code is loaded from the shared folder. Only the shared folder of the associated installation is used; other drives are not scanned and backends are not switched. The change takes effect after that local backend restarts; backends that disabled SwarmUI's built-in node pack must configure model paths themselves.

If a model file is in the shared folder but you get `ckpt_name not available`, first check whether the backend has loaded the shared folder; there is no need to download the same model again. Shared models are available to native workflows but are not added automatically to the global model list of SwarmUI's standard workspace.

Workflows found in other installations are only imported as templates; that installation is not started or switched to. The server a workflow was discovered on only indicates its source; the actual generation is assigned by the scheduler to an execution server that has the required nodes, models, text encoders and VAE (see "Execution server scheduling" below). A native workflow appears in the list only when at least one online execution server has every node and model its saved configuration needs; dependencies of several servers are never combined. While no server is ready or dependencies are missing, it is hidden, and later refreshes check again. This check does not mean the model combination has been verified or that GPU generation has succeeded. Leaving the prompt empty by default does not filter a workflow out.

A native workflow's ID is `source/relative path`, and the workspace drop-down groups workflows by source. The source is the name of the execution server it belongs to (the backend Title, or `本机 #N` / `服务器 #N` when none is set); local installations that do not belong to a registered server use the installation folder name. IDs are cleaned with SwarmUI's workflow file name rules: characters such as `.`, `#`, `&` and `%` and spaces around `/` are removed, and `/` inside the server name becomes `-`. This keeps the ID unchanged when SwarmUI cleans the name again at generation time; otherwise the workflow could not be found. Native entries with the same execution graph, parameter definitions and defaults are shown only once, keeping the one that sorts first by name; deduplication never deletes or rewrites the original files. On name conflicts an 8-character short hash computed from the source path is appended, for example `(1A2B3C4D)`. If a workflow still does not appear after a refresh, make sure the file is saved in one of the directories above, the selected image/video type is correct, and the workflow meets the import conditions; merely opening the editor canvas or starting a backend does not mean the workflow has been saved and validated.

The workspace "Task queue" page shows, per execution server, the running tasks, waiting tasks, current node and node progress; waiting tasks include tasks the platform has assigned to that server but not yet handed to ComfyUI. A server running a task with nothing waiting is marked "Working" (yellow light), and a server with a queue is marked "Congested" (red light). Accounts with generation permission can end active tasks they started; queue information is kept only while the service runs, and no persistent history is provided.

## Execution server scheduling

On each submission the platform chooses one execution server by the following rules, and all images of one submission run on that server:

1. Only servers that are online and have every node and model the task needs are considered. In the standard workspace mode SwarmUI builds the node graph, so LAN servers take part only if they have the SwarmUI ComfyUI nodes installed; published native workflows are judged by their own dependencies.
2. Among those servers, the one with the shortest queue is chosen; on a tie, the one that finished a task longest ago. Queue = tasks running and waiting in that server's ComfyUI (including tasks others submitted directly to that ComfyUI) + tasks the platform has assigned to it but not yet handed to ComfyUI. The latter is an estimate and may be undercounted for a few seconds while a task is being posted to ComfyUI.
3. With two or more execution servers, the creation panel shows an "Execution server" drop-down, defaulting to "Automatic (recommended)". If you choose a server, the task queues only on that server and is never reassigned; if that server is offline or lacks dependencies, you are told directly and the task is not submitted. If the chosen server has a queue while another capable server is idle, a hint suggesting removing the restriction appears after submission.
4. When no server can run the task, it is not submitted and the reason is given: all servers are offline, or which nodes and models each online server lacks (at most 3 per server).
5. After a successful submission the status bar shows the name of the server that runs the task; the name is also written into the work's metadata, and the gallery shows "workflow｜execution server" under each work's time (works from the standard workspace show "标准工作台", standard workspace).
6. When the executing server drops off or a task fails, the platform never retries automatically. The workspace shows the reason and a "Reassign to another server" button; clicking it submits the same request again without the server restriction, and the rules above choose again. The request is kept only in page memory, so after a reload only the reason is shown; uncertain results are never offered for reassignment, so check in the native engine first to avoid duplicate generation.

Scheduling only happens among registered execution servers and never moves to unregistered addresses, remote SwarmUI instances or cloud services. The scheduling layer is built on an "executor" abstraction that reserves two types, cloud ComfyUI and cloud model APIs; they are not implemented in this phase and no request is ever sent to them.

## E-commerce scene templates

A template wraps a published workflow snapshot as an e-commerce scene that shop staff can use directly, such as "White background main image" or "Lifestyle scene". A template has no node graph of its own; it references a published snapshot and uses that snapshot's parameter allowlist:

```json
{
  "id": "white-main",
  "name": { "zh-CN": "白底主图", "en": "White background main image" },
  "description": { "zh-CN": "纯白背景，适合平台主图", "en": "Pure white background for main images" },
  "example_image": "white-main.webp",
  "platforms": ["amazon", "taobao"],
  "sets": ["main-set"],
  "prompt": { "prefix": "product photo,", "suffix": "soft studio light", "negative": "text, watermark" },
  "categories": [],
  "brand_kit": null,
  "execution_plans": [
    { "kind": "local", "workflow": "B/white-main", "presets": { "parameterId": 30 }, "user_fields": ["parameterId"] }
  ],
  "enabled": true
}
```

- `id`: lowercase letters, digits and hyphens; `name` needs both Chinese and English, `description` is optional.
- `platforms`: IDs of the platforms the template suits, or `"*"` for any; `sets`: IDs of the image sets it belongs to, used by one-click sets.
- `prompt`: prompt fragments added before and after the user's description, and a negative prompt; `<…>` directives and `__wildcards__` are not allowed.
- `execution_plans`: in this phase every template needs exactly one local plan (`kind` is `local`), whose `workflow` is the ID of a published snapshot. `presets` fixes snapshot parameter values and cannot preset the prompt or an image; `user_fields` are the parameters users may change, which must be visible after review and not preset. Cloud plans (`cloud_comfy`, `cloud_model_api`) are reserved and rejected in this phase.
- `preserve_product` (optional, default `false`): product preservation. When on, the product photo users upload must be a cut-out with a transparent background (PNG or WebP); the platform crops the cut-out to the product (keeping a 2% transparent margin), places it on a canvas of the output size locally and passes it as the template's product image parameter; the canvas is white but fully transparent around the product, so workflows that read its alpha (the standard workflows) generate only the scene around the product, while workflows that read only its colors see the product on white; after generation it pastes the original product pixels back onto every result at the same placement (the edge is softened inwards by 2 pixels), overwriting the saved works while keeping their metadata, so the product's logo, text and shape cannot be changed by generation. The template must then open an image parameter to users. The placement can be given in the request as `placement` (`x`, `y`: the product center as fractions of the picture width and height, 0–1; `size`: the product's longer side as a fraction of the picture's shorter side, 0.1–1.5); the default is horizontally centered, a little below the middle (y 0.56), at size 0.55. The system-generated standard workflows fill the transparent part of the canvas with neutral gray, grow the repainted area slightly into the product, generate the scene, put the product on it and sample the whole picture again at low strength (0.35, 10 steps) to unify light and edges; the final paste then takes details (logo, text, shape) from the original and light and color from the generated picture (at most 40 per color channel), with a contact shadow under the product. Other workflows still get the exact paste described here. Since the cut-out is cropped first, the size is the product's own and not that of the photo's transparent border. The standard workflows refuse an opaque product image, which would come back unchanged. Workflows do not need to output a product mask; the cut-out is kept only in memory, for at most two hours.
- `requirements` (optional): the models and nodes the template needs. Each item of `models` is `{ name, folder, commercial, license_url, download_url }`: `name` is the model file name (it may include a subfolder but no `..` or backslash), `folder` is the folder under ComfyUI's `models` (for example `checkpoints`, `loras`, `vae`), `commercial` is the commercial-use license status `allowed`, `forbidden` or `unknown` (the default), and both links must be http or https. `nodes` lists ComfyUI node class names. Administrators install models by hand on each server (assumption A2); the platform does not download them across servers.
- `cutout_only_platforms` (optional): on these platforms no generation model is called; the product cut-out is centered on pure white (RGB 255,255,255) with its longer side at about 85% of the picture's shorter side, at the size of the platform's white-main slot (F58; the platform's default slot when it has no white slot, else 2000×2000), and saved as a work in the gallery. The built-in white background main image does this for `amazon`. Requests must carry `platform`. Such works are marked as cut-outs and get no AI-generated marking on export.
- `kind` (optional, F58): the image slot kind the template serves — `white_main`, `scene_main`, `detail`, `model` or `video_cover` (the video-cover kind only records its spec this phase). When a platform defines slots, one-click sets compose templates by slot kind; templates without a kind do not join slot-composed sets. The template list API returns each template's `slot_kind`.
- `categories` (category presets) is reserved. `brand_kit` (the brand kit slot, F12) is `null` or `{ "reference_image": "parameter ID", "logo_image": "parameter ID" }`: both must be image parameters of the workflow snapshot, may not also be open to users (`user_fields`) and may not be the same parameter. When a brand kit is chosen, the server fills them with the kit's first reference image and its logo; templates without the slot only use the kit's prompt fragment (brand colors and preferred background). Clients send only `brand_kit_id` with `EcomCraftStudioGenerate` and `EcomCraftStudioGenerateSet`; a kit that does not belong to the account returns `invalid_brand_kit`.

There are 4 built-in templates: White background main image (`white-main`), Lifestyle scene (`scene`), Detail close-up (`detail`) and Model or hand-held (`model`), for every platform and all in the image set `standard`; the first three preserve the product, while the model template does not because poses and angles change. They reference workflows by convention: `workflow` is written like `*/ecomcraft/white-main`, meaning the published workflow at path `ecomcraft/white-main` on any execution server (the first by ID when several exist), and `@image` in `user_fields` means the workflow's first visible image parameter, which receives the product photo. The workflows are made by outside experts; once saved under the conventional name in an execution server's ComfyUI and approved, the template becomes available automatically. Until then it is hidden and the management API reports a missing workflow. Example images go in the same folder as `<template ID>.webp` and are referenced by `example_image`.

Built-in templates ship with each release in the extension folder `Templates/builtin/` (one template per file, example images in the same folder); administrator templates are stored in `Data/EcomCraft/templates.json` with example images in `Data/EcomCraft/template-images/`. The two are kept apart, so upgrades never overwrite custom templates, and a custom template cannot reuse a built-in ID.

Invalid templates are never offered to users; the reasons are written to the server log and returned by the management APIs. A template also shows as unavailable when its snapshot is unpublished, a parameter is hidden, or a preset is out of range. The management APIs require the review permission (`ecomcraft_review_workflows`): `EcomCraftTemplateAdminList` lists every template with the reasons it cannot run, `EcomCraftTemplateSave` adds or replaces an administrator template (`template` is the template JSON; optional `example_image_data` is a PNG, JPEG or WebP image of at most 2 MB), and `EcomCraftTemplateDelete` removes an administrator template. `EcomCraftTemplateRequirements` lists the models and nodes each template needs, each model's commercial-use license status and which execution servers lack them (compared with the model files and nodes in each server's object info; servers are given by ID and name only). The "Models templates need and commercial-use licenses" section of the workflows page shows this, with "Commercial use forbidden" and "License unknown" highlighted.

## LAN execution servers

A LAN device with only ComfyUI installed can be registered as an execution server and called by the platform server. For account login, firewalls and shared storage when several people use the platform, see the [LAN Deployment Guide](EcomCraft%20LAN%20Deployment.md). For the development plan and upcoming features, see [LAN Multi-Server Platform Requirements](EcomCraft%20LAN%20Multi-Server%20Platform%20Requirements.md).

1. Start ComfyUI on the LAN device with `--listen 0.0.0.0` (you can also choose the port with `--port`); otherwise ComfyUI only accepts local connections.
2. In that device's firewall, allow only the platform server to reach the ComfyUI port. ComfyUI has no login of its own; do not open the port to the whole LAN or the internet.
3. On the platform server, add a `ComfyUI API By URL` backend under **Server → Backends** in the native engine, enter its address (for example `http://192.168.1.21:8188`), and enter a display name (for example "B") as the backend title. Ordinary users see only the display name, never the address. Set the name before reviewing its workflows and do not change it afterwards: workflow IDs start with the server name.
4. After saving, wait until the backend status becomes `RUNNING`. Within about 30 seconds, the workflows saved in that device's ComfyUI appear in the list.

Only the following addresses are treated as execution servers: loopback addresses, private-range IPs (`10.x`, `172.16–31.x`, `192.168.x`, `169.254.x`, IPv6 unique-local / link-local addresses), and host names without a dot or ending in `.local`, `.lan`, `.home.arpa` or `.internal`. Any other address (including public domain names) is never used by the workspace even if registered as a backend. Other backend types such as remote SwarmUI are not used either.

After a task finishes, the platform server fetches the results through ComfyUI's `/history` and `/view` endpoints, saves them to the current user's output folder and shows them in the gallery; reference images are uploaded to the execution server first. This return path has not yet been verified on a real LAN device.

## Client API

Create a SwarmUI session first, then call `POST /API/EcomCraftStudioGenerate`. Submit only the workflow ID and published parameters, never raw ComfyUI JSON:

```json
{
  "session_id": "current session ID",
  "source": "local",
  "kind": "image",
  "mode": "text2img",
  "workflow_id": "Examples/my_product_workflow",
  "workflow_params": {
    "product_style": "clean studio",
    "reference_image": "data:image/png;base64,..."
  },
  "model": "official model name",
  "prompt": "a bottle of skincare product, commercial product photography",
  "negativeprompt": "blurry, low resolution",
  "width": 1024,
  "height": 1024,
  "images": 1
}
```

Optional fields include `seed`, `steps`, `cfgscale`, `sampler` and `scheduler`. Video workflows use `kind: "video"` and submit `text2videoframes` as the workspace requires; each batch can generate only one video.

`execution_server_id` (optional, integer) restricts the task to one execution server; its value is `backends[].id` from the queue API. Omit it for automatic assignment. The server only accepts IDs of registered execution servers; SwarmUI's native backend selector parameters (such as `exactbackendid`) are still rejected. With `async: true` the call returns `queued` and `task_id` right after submission. Every successful response includes `execution_server` (the display name of the server that runs the task, never its address), plus `server_hint` when the chosen server is congested while another is idle. Scheduling error codes: `invalid_execution_server` (the ID is not a registered execution server), `execution_server_unavailable` (the chosen server is offline or lacks dependencies; the task was not reassigned) and `no_execution_server` (no server can run the task; `error` explains why). Exceeding the `MaxQueued` limit of the account's role returns `queue_limit` and the task is not submitted (see the [LAN Deployment Guide](EcomCraft%20LAN%20Deployment.md#4-per-person-queue-limit-r92)).

Before calling, you can read `POST /API/EcomCraftStudioCatalog`; the workflow list is in the `workflows` field of the result, where `inputs` describes each fillable parameter's ID, type, default value and allowed options. Clients should build `workflow_params` from this list and must not guess parameter names. The catalog also returns `can_review_workflows` and `can_submit_workflows`, which say whether the current account can review or submit workflows. Workflows the account uploaded itself (F60) are also in `workflows`, marked `own: true`, and are returned to the uploader only. Upload with `EcomCraftStudioWorkflowUpload` (`name`, and `workflow` as the JSON text saved with ComfyUI's Save, up to 2 MB); failures carry the `error_id` `workflow_api_format`, `workflow_unsupported`, `workflow_denied` (with `problems: [{ code, node, input }]`, `code` being `denied_node` or `path_value`), `workflow_too_large` or `workflow_limit`. `EcomCraftStudioMyWorkflows` lists one's own workflows with the execution servers that can run them (names and missing nodes or models only), and `EcomCraftStudioWorkflowDelete` (`workflow_id`) deletes one. `EcomCraftStudioWorkflowSubmitOwn` (`workflow_id`, optional `note`) submits a never-submitted or rejected own workflow for review; list entries carry `review_state` (`draft`, `pending`, `rejected`, `published`) and, when rejected, a `reject_reason` for the uploader only. Reviewers see it in `EcomCraftStudioReviewList` as a pending item with `upload: true` and the source "账号上传"; approving it with `EcomCraftStudioReviewDecide` returns `published_id` (`上传/<name>`), a copy handled like any published workflow (it can be unpublished). None of these ever return the graph.

Standard workflows (F57): `EcomCraftStandardWorkflows` (server-settings permission, optional `action: "init"`) returns the state of the scene and detail standard workflows (`published`, `taken_down`, `missing_blueprint`, `unsupported`, `missing_dependencies`, `no_server`, `failed`, `not_checked`), missing node or model names and the default model names; `init` generates and publishes them now (including ones taken down). They are published as `系统生成/ecomcraft/scene` and `系统生成/ecomcraft/detail` with an image parameter `ecproductimage` for the templates' `@image`. The graph loads it (N10, first step): the product canvas is transparent around the product, `LoadImage` turns its alpha into the mask, and `SetLatentNoiseMask` limits sampling to the scene around the product, so surface, shadows and scale follow the real product; the product is still pasted back after generation. Image parameters skip the file-list check, since the backend uploads them at generation time. The review APIs are `EcomCraftStudioReviewList`, `EcomCraftStudioReviewDetail` and `EcomCraftStudioReviewDecide` (`action` is `approve`, `reject` or `unpublish`); the submission APIs are `EcomCraftStudioWorkflowSubmissions` and `EcomCraftStudioSubmitWorkflow`. They return only parameter definitions, states and the names of missing nodes or models, never the raw node graph or server addresses. Review error codes include `invalid_review` (invalid configuration), `workflow_state` (the current state does not allow the action, or someone else just changed it) and `review_save_failed` (the record could not be saved). Read `POST /API/EcomCraftStudioQueue` for each execution server's queue (`backends[]` contains `id`, `name`, `status`, `running`, `pending`, `assigned` (tasks the platform assigned but has not yet handed to ComfyUI), `queue` (the queue used for scheduling), `load` (`idle`, `working` or `congested`; `null` when the queue cannot be read) and `busy` (same as `load` being `congested`), and no address) and the current generation tasks, plus `finished_tasks` (the current account's background tasks that ended in the last 15 minutes: `id`, `state` as `done` or `failed`, `error`, `error_id` and `execution_server`, never other accounts' tasks); to end a generation task of the current account, call `POST /API/EcomCraftStudioCancelTask` with the task `id` returned by the queue.

Read `POST /API/EcomCraftStudioTemplates` (optional `language`: `zh-CN` or `en`) for the e-commerce scene templates the current account can run: `templates[]` contains only `id`, `name`, `description`, `example_image` (URL of the template's example image), `kind`, `platforms`, `sets` and `fields` (the parameters users may change, in the same format as a workflow's `inputs`); templates that cannot run are listed under `hidden[]` with `reason` `invalid` (invalid template configuration) or `unavailable` (no online server can run it, or the account may not use its models), and reviewers also get a `detail` explanation. To generate from a template, send `template_id` and optional `template_params` (parameter ID to value, only the template's `fields`) to `EcomCraftStudioGenerate`, along with ordinary fields such as `prompt`, `negativeprompt` and `images`; the server resolves the template into a published snapshot, preset parameters and prompt fragments, then checks them against the snapshot allowlist, ignoring any `workflow_id` and `workflow_params` from the client. An optional `seed` (a non-negative integer) only sets the snapshot's seed parameter and is still checked against that parameter's range, so "Make again with same settings" can reproduce a filed work. Unavailable templates return `invalid_template` or `no_execution_server`, and the work's metadata records `ecomcraft_template`.

Prompt service: `EcomCraftStudioStyles` (optional `language`) returns the visual styles users can pick (`id`, `name`, `description`); `EcomCraftStudioComposePrompt` (`style_id`, `description`, optional `product_image`) turns a style and a one-line description (Chinese or English) into an English prompt with the configured prompt enhancement model, returning `prompt` and `source` (`model` or `template`); when the model is unavailable or does not answer within 45 seconds, the style defaults are used and `notice` and `notice_code` are returned (`description_used` when the English description was used as is, `description_unused` when a Chinese description could not be used this time). When generating from a template you may also omit `prompt` and send `description` and `style_id` instead; the server builds the prompt and the response carries `prompt_notice` / `prompt_notice_code`. Bilingual prompt panel of the simple mode (F54): `EcomCraftStudioExpandPrompt` (`description`, `product_type_id`, `style_id`, `need_model`) expands the one-line description (or, when empty, the product type) into an English prompt `prompt_en` and its Chinese version `prompt_zh` (empty when the translation failed), and returns the error code `prompt_service_unavailable` when the model is unavailable. Template generation (`EcomCraftStudioGenerate`) and one-click sets (`EcomCraftStudioGenerateSet`) accept `prompt_en` (English edited by the user, cleaned and used as is) or `prompt_zh` (Chinese edited by the user, translated into English by the server), up to 1500 characters each; when both are empty, `description` is composed as before. The fixed product-type, model and style fragments are always added by the server. Successful responses carry the English prompt actually used as `prompt_used`, plus `prompt_translated` when Chinese was translated; when the translation fails the product-type and style defaults are used and `prompt_notice_code` is `prompt_untranslated`. These fields appear only in answers the submitter alone can read (the submit response, `EcomCraftStudioPrepareStatus` and their own batch status); the shared queue API never returns prompts. Faster submission (F56): when the model has to write the prompt or translate Chinese, `EcomCraftStudioGenerate` returns `prepare_id` and `stage: "prompt"` at once (`task_id` is empty), writes the prompt in the background (the model keeps its 45-second limit and falls back to the defaults), and then submits as usual; the client polls `EcomCraftStudioPrepareStatus` (`prepare_id`) for the stage `prompt`, `submitted` (with the usual submit answer: `task_id`, `execution_server`, `prompt_used`…) or `failed` (`reason`, `reason_id`). Entries are visible to their owner only and kept for 10 minutes; each account may have at most 5 submissions waiting for their prompt, beyond which `queue_limit` is returned. English panel text, an unchanged expansion and plain ASCII text skip the model and are still submitted directly. `EcomCraftStudioGenerateSet` returns the batch at once with its tasks in state `prompt`; once the prompt is composed they move to `queued` and start. The batch status carries `prompt_ready` and, when ready, `prompt_used` and related fields; tasks in state `prompt` can be cancelled. Selling points and set storyboard (F25): `EcomCraftStudioStoryboard` (`description`, `selling_points` (one per line, at most 5), `product_type_id`, `style_id`, `need_model`, `platform`, `language`, optionally `prompt_en` / `prompt_zh`) returns `selling_points`, `shots` (each with `template_id`, `template_name`, `prompt` (an English scene fragment) and `purpose`), `source` (`model` or `fallback`) and `notice_code` (`storyboard_fallback` when the model is unavailable, in which case the platform's standard set gives one shot per type). The model may only answer in a fixed line format; the server drops unknown templates and anything else, and cleans fragments with the prompt rules. `EcomCraftStudioGenerateSet` accepts `shots` (at most 8, each with `template_id`, `prompt`, `purpose`) instead of the set templates: each must be a registered template available on the platform, otherwise `invalid_template` is returned; tasks expand as products × shots, still within the 20-image cap; Chinese fragments are translated in the background, a fragment that cannot be translated is left out and the batch status carries `shots_untranslated`; tasks carry `purpose`. The model's answer only ever becomes prompt text: the server removes native directives, wildcards, quotes and extra paragraphs, so it cannot affect the workflow, parameters or execution server. Sending product photos to a vision model to describe the product is off by default; only administrators with the server-settings permission can turn it on through `EcomCraftPromptSettings` (`vision_enabled` `true` / `false`), which also returns the provider (`vision_provider`) and model the photos would be sent to.

Cut-out: `EcomCraftStudioCutout` (`product_image`: a PNG, JPEG or WebP data URL of at most 5 MB) removes the background on a registered execution server that has the SwarmUI nodes (`SwarmLoadImageB64`, `SwarmRemBg`, `MaskToImage`, `PreviewImage`), chosen by Rule 1; the server builds the fixed node graph itself and clients cannot send one. The server fetches only the mask and combines it locally with the user's own photo into a PNG with a transparent background (`cutout`), so the product pixels are the original ones. When no server has these nodes it returns `no_execution_server`, and failures return `cutout_failed`; a PNG with a transparent background can also be uploaded directly. For templates with product preservation, the simple mode shows a cut-out confirmation where users can remove the background, drag the product and resize it; the request then carries `placement`.

One-click sets and batches: `EcomCraftStudioGenerateSet` (`products`: 1–20 product photos, each `{ image, placement? }`; `platform`; `set_id`, default `standard`; `style_id`, `description`; `candidates`: candidates per image type, 1–20; optional `optional_slots` (the ticked optional slot IDs), `execution_server_id` and `language`) expands every product photo × the set's templates into independent tasks, at most 80. When the platform defines image slots (F58), the set is composed by slot kind: every non-optional slot's kind is generated, ticked optional slots add theirs, and each kind is generated once; platforms without slots keep every template of the set that suits the platform. Ticking an optional slot that does not belong to the platform returns `invalid_parameters`. The prompt is composed once for the whole batch; cut-outs needed by preserving templates are made by the server (photos that are already transparent are used as is). Each task goes through the normal template generation, so it passes the same snapshot allowlist checks and is scheduled by Rule 1 on its own, possibly on several servers in parallel; each person runs at most the smaller of their role's `MaxT2ISimultaneous` and 4 tasks at once (requirement R9.4), and the rest wait inside the platform. It returns `batch_id` and `jobs[]` (`id`, `product`, `template`, `template_name`, `state` as `queued` / `running` / `done` / `failed` / `cancelled`, `error`, `error_id`, `execution_server`, `images`). `EcomCraftStudioBatchStatus` reads progress, `EcomCraftStudioBatchRetry` (`batch_id`, `job_id`) retries a failed or cancelled task, and `EcomCraftStudioBatchCancel` cancels the tasks still waiting (running ones finish). Batches are kept only in memory for six hours and only their owner can see them.
Reference images (F59, a standalone mode): `EcomCraftStudioReferenceDescribe` (`reference_images`, 1–8 image data URLs) has the vision model describe every reference, returning `items: [{ index, prompt_en, prompt_zh }]` and `failed` (how many failed; the Chinese translation may take up to 90 seconds, and when it times out `prompt_zh` is empty while the English description is still returned); the page shows one prompt per reference with the English editable (edits win). When an administrator turned image description off it returns `vision_disabled` (it is on by default). `EcomCraftStudioVisionStatus` (no parameters) returns `state` (`ready`, `off`, `no_model`, `unreachable`, `model_missing`), `provider`, `model` and `can_manage`, never the vision service address or key, so the page can explain what "Follow a reference" is missing. Administrators can switch the vision model right on the reference page: `EcomCraftStudioVisionModels` (no parameters) returns `models` (the names of the models the vision service offers that can read images; on Ollama only models with the vision capability), `model` and `provider`, or `vision_unreachable` when the vision service cannot be reached; `EcomCraftStudioSetVisionModel` (`model`) only accepts a model the vision service lists (otherwise `invalid_vision_model`) and saves the same vision model as the prompt enhancement settings. Both need the server settings permission and never return the vision service address or key. Device self-test for a local Ollama vision model (F71 P2): `EcomCraftPromptSettings` returns `vision_check` (`state` none / running / done / failed, plus `device` and `seconds`), and `EcomCraftStudioVisionDeviceCheck` starts a new test (server settings permission; returns `vision_check_unavailable` when the vision service is not Ollama, the device is not automatic or Ollama is not running). Every image description writes one line with the service type and model actually used to the server log (no address, key or image). Submission goes through `EcomCraftStudioGenerateSet` in reference mode: `reference_prompts` (one English prompt per reference, required, cleaned server-side) plus optional `reference_images` (kept briefly in the in-memory batch only, never written under `Data/`) and optional `reference_placements` (as long as the prompts, each `{ x, y, size }` or `null`; when not `null` that reference's tasks use it instead of the product placement, validated like product placements); one image per reference per product (the candidate count is fixed at 1 and the image type, style, model checkbox, brand kit, description and storyboard do not apply), always with the `scene_main` template, mutually exclusive with `shots` (submitting both returns `invalid_parameters`); tasks carry `reference_index` so the page can show the reference thumbnail. A reference task's prompt is sent exactly as the user saw it, without the template's fragments, and the task card shows the prompt actually used.

Product library: `EcomCraftStudioProducts` lists the current account's saved products (`id`, `name`, `created`, `has_cutout`, `placement`, and `image` / `cutout_image` URLs, never file locations); `EcomCraftStudioProductSave` (`image`, optional `name` and `cutout`) saves a product; `EcomCraftStudioProductUpdate` (`product_id`, optional `name`, `cutout`, `placement`) renames it or stores the confirmed cut-out and placement; `EcomCraftStudioProductDelete` removes a product and its files. Product files are stored under `products/<account>/<product ID>/` in the work library location, or in `Data/EcomCraft/product-files/` on the platform server when no work library is set, and never in the gallery; the index is `Data/EcomCraft/products.json`. Products are isolated per account, and the image URLs `/EcomCraft/product-image/<ID>/original|cutout` are only served to the owner. Template generation and one-click sets accept `product_id` instead of an image: the server reads the original photo or the confirmed cut-out and placement, and clients never send files or paths. In the simple mode uploaded products are saved automatically, updated when the cut-out and placement are confirmed, and can be picked next time from "Choose from the product library".

Output size (F73): template generations (`EcomCraftStudioGenerate` with `template_id`, and `EcomCraftStudioGenerateSet` for sets, storyboards and reference mode) accept `output_size: { width, height }` (whole numbers 64–8192); without it the size is the chosen `platform`'s slot size for the template's image kind, and without such a slot the workflow's own size applies. The workflow runs at the same aspect ratio near one megapixel (sides multiples of 16, 256–2048) and the works are scaled locally to the exact size before the original product is pasted back at that size (so scaling never blurs the product); `resize_failed` counts works that could not be scaled. `EcomCraftStudioPlatforms` returns each slot's `width` and `height`. `EcomCraftStudioExport` with `keep_size: true` keeps each work's own size and takes format, quality, size cap and the white check from the platform's slot for the work's image kind (read from its template marker).

Platform export (F58, slot-based): platform presets live in `Templates/platforms.json` in the extension folder (administrators can override them with a file of the same format at `Data/EcomCraft/platforms.json`). Each platform consists of image `slots` with the fields: `id`, `kind` (`white_main`, `scene_main`, `detail`, `model` or `video_cover`; video covers only record their spec this phase), localized `name`, `width`, `height`, `background`, `format` (jpg or png), `quality`, and the optional `max_bytes` (per-file size cap; JPEGs over it are re-encoded at a lower quality, twice at most, and exported anyway with a notice), `subject_ratio_min` (hint floor for a white slot's subject fill; never blocks), `position` (which image the white one is best placed as; a hint) and `optional` (optional slots: their kind joins image sets only when ticked). Platform-level fields: `main_image_count` (hint), `forbidden` (forbidden content; when it includes `promo_text`, exporting images with drawn text shows a notice), `ai_label` (AI labelling policy; `platform_declaration: true` hints that AI-generated images must be declared in the seller portal), `source` and `verified`. Old single-preset files (an `export` object only) keep working as one main slot, with `require_white_background` becoming a white-main slot. The built-in values come from commonly published platform requirements and are all marked unverified; check them against the platforms' current rules (N06) and set `verified: true` before use. `EcomCraftStudioExportOptions` (optional `language`) lists the platforms with their slots (ID, kind, localized name, size, optional flag) and whether exporting to the shared folder is available; `EcomCraftStudioExport` (`platform`, `slot` as the target slot ID (defaulting to the first non-optional slot), `target` as `zip` or `folder`, and `groups` as `[{ name, images }]`, where `images` are the user's own gallery paths, result URLs or `{ url, slot }` objects naming a slot per image, at most 200) scales each work to fit its slot, centers it and pads it with the background color (transparent areas show the background too), one folder per group: `zip` returns a `download` URL (only the owner can download it, kept for one hour), and `folder` writes to the administrator's export location under `<account>/<time-platform>/<product>/`. White slots (or slots with an explicit `require_white`) check the outer border for pure white; files that fail are listed in `not_white` and flagged in the workspace. Hinting results come back as `warnings` (`size_over` still over the size cap after re-encoding, `subject_small` below a white slot's subject fill, `text_image` images with drawn text on a platform forbidding `promo_text`), plus `ai_declaration: true` when the platform asks for a declaration; the page words them in its language. Error codes are `invalid_export` and `export_failed`. On export, AI provenance metadata is written according to how each work was made (XMP `Iptc4xmpExt:DigitalSourceType`, `xmp:CreatorTool`, `dc:description`; EXIF `Software`, `ImageDescription`): ordinary generated pictures get `trainedAlgorithmicMedia`, product-preserving composites (original product pixels + generated background) get `compositeWithTrainedAlgorithmicMedia`, and cut-out-only main images get none.

Selling-point images (F47): `EcomCraftStudioSellingImage` (`image` is a gallery path or result URL of the account's own work, `layout` is `banner`, `side` or `badges`, `title` has up to 20 characters, `points` up to 3 items of at most 16 characters, optional `accent` as `#RRGGBB`) draws the text on the server with the Noto Sans SC fonts in `Assets/fonts` and never calls a generation model; the result is saved as a new PNG work (`ecomcraft/selling/…`) that keeps the original's metadata plus an `ecomcraft_selling_image` marker, and `images` is returned. Invalid text returns `invalid_selling_text` (also naming characters such as emoji that the fonts cannot draw); missing font files return `selling_font_missing`.

Project archive (F04): `EcomCraftStudioProjects` lists the account's projects; `EcomCraftStudioProjectSave` (omit `project_id` to create, `name` up to 40 characters, `note` up to 200); `EcomCraftStudioProjectDelete` (`project_id`, removes the record only, works stay in the gallery); `EcomCraftStudioProjectAddWorks` (`project_id`, `images` with up to 100 gallery paths or result URLs, optional `product_id`, `brand_kit_id`, `platform`; IDs that do not belong to the account are dropped); `EcomCraftStudioProjectRemoveWorks` (`project_id`, `images`); `EcomCraftStudioProjectWorks` (`project_id`) returns each work's address, `exists` and recipe (`template`, `seed`, `prompt`, `execution_server`, `width`, `height`, `product_id`, `brand_kit_id`, `platform`). Recipes are only read from the work file's own metadata, never from client-submitted parameters; the prompt is kept without the template's prefix and suffix. Records are readable by their owner only and stored in `Data/EcomCraft/projects.json`, which is never overwritten when it cannot be read; a failed save returns `project_save_failed`. `EcomCraftStudioWorkRecipe` (`image` is a gallery path or result URL of one's own work) reads the full prompt sent to the engine and the size from the work's own metadata for "Refine in professional mode" (F64); another account's work returns `invalid_reference`. The workspace gallery (T10) uses these APIs to switch the current project, filter by project and add or remove works; "Make again with same settings" only fills the recipe into the simple mode, and the submission is still an ordinary template request (`template_id`, `prompt`, `seed` and the product ID) that the server checks again.

Candidate retention and cleanup: images generated in the simple mode are registered on the platform; candidates that were never picked, downloaded or exported are deleted by a background pass after the administrator's retention time (14 days by default, 0 disables it), after verifying the path stays inside the owner's works folder with a picture or video extension. When the user picks or downloads a candidate, the client calls `EcomCraftStudioMarkKept` (`images` as the owner's gallery paths or result URLs, at most 500) to drop it from the registry; platform exports mark automatically on the server. Professional-mode results are never registered and never cleaned.

Upload quality thresholds: `EcomCraftStudioPlatforms` returns `quality` (`min_side`, `blur_variance`, `min_cutout_ratio`) — the `upload_quality` block of `platforms.json`. Clients use it to warn about low resolution, blur or a product that fills too little of the frame; the user can always continue. The API also returns each platform's slot summary (`slots`: `id`, `kind`, localized `name`, `optional`, `position`) and `main_image_count` (F58), so the page can hint where the white image goes and offer optional-slot checkboxes.

Operations APIs (administrators): `EcomCraftDiagnostics` builds a diagnostics zip (recent logs, execution-server status, versions and sanitized configuration; keys, passwords, tokens, prompts, images and session data are removed) and returns a `download` URL (`/EcomCraft/diagnostics/<id>`, downloadable only by its creator, kept one hour). `EcomCraftBackupCreate` packs `Data/EcomCraft` and the account database into a zip with a SHA-256 manifest (`/EcomCraft/backup/<id>`, kept one day); `EcomCraftBackupRestore` (`data` as base64 backup content, requires `confirm: true`) validates every file before restoring, parks locked account database files in a staging folder for a swap while stopped, and returns `restored`, `staged` and `restart_required`. Error codes: `backup_failed`, `backup_invalid` and `backup_confirm_required`.

Estimated time remaining (F70): the server keeps the actual durations of the last 20 runs of each kind of operation in memory (seconds only, never prompts, images or other content; cleared on restart) and estimates by the median. `EcomCraftStudioEstimates` returns the typical seconds of writing a prompt (`compose`), AI expansion (`expand`), a storyboard (`storyboard`), describing one reference image (`describe`) and the professional-mode prompt enhancement (`enhance`), `null` before the first run. Generation keeps the per-image time by "workflow or model + size + execution server" (the time from submit to result divided by the tasks queued ahead at submit plus its own images). `EcomCraftStudioPrepareStatus` returns `elapsed_seconds`, `estimate_seconds` and `remaining_seconds` while the prompt is written; `EcomCraftStudioBatchStatus` returns the same fields with a `prompt_` prefix while the batch prompt is written, and running tasks carry `elapsed_seconds`, `estimate_seconds`, `remaining_seconds` and `start_in_seconds`; `EcomCraftStudioQueue` adds these fields to the current account's own tasks only. A `remaining_seconds` of 0 means slower than usual, and the page shows "slower than usual, still working…".

Disk space: the free space of the platform server's output folder and the work library is checked in the background (thresholds in the storage settings: 10 GB warning and 2 GB critical by default, 0 disables). When critically low, `EcomCraftStudioGenerate` and `EcomCraftStudioGenerateSet` reject with `disk_full`; `EcomCraftStudioQueue` additionally returns `disk` (`level`, `output_free_gb`, `library_free_gb`) to administrators.

Instantly finished tasks: a generation that fully hits ComfyUI's cache can end before the submit request returns; such a response carries no `task_id` but includes `images` directly (like the cut-out-only branch), and the works are still saved to the gallery. Clients should handle both response forms.

Native imported entries additionally return `native: true` and `defaults`. `inputs[].form` marks parameters bound to standard page fields (such as `width` and `seed`); other inputs are submitted through `workflow_params`. When a standard field is omitted, the corresponding published parameter or saved default is used; when both are given, the standard field wins. Native entries do not need a root-level `model`; model changes are submitted through the ID of the model drop-down in `inputs`, and the server accepts only the published options. Parameter IDs are opaque identifiers; clients must not construct them.

## Security boundaries

- The workspace uses only registered execution servers (the local self-starting ComfyUI and `ComfyUI API By URL` backends with LAN addresses) and never switches to unregistered addresses, remote SwarmUI or cloud services because an execution server is unavailable.
- The server re-checks whether the workflow is published, whether parameters are on the allowlist, and whether models and images are within what the current account may use.
- Default images in published workflows are never reused automatically; each client must upload its own image parameters.
- To edit the raw node graph, use unpublished workflows or debug nodes, use the ComfyUI workflow page of native SwarmUI and grant the corresponding administrator permissions.

## Startup fails after changing the local backend

If the log shows `huggingface-hub>=1.5.0,<2.0 ... found huggingface-hub==2.3.0`, this is a Python package version conflict. When the launcher updates diffusers, it passes the installed transformers and tokenizers versions to pip's resolver as well, so dependency upgrades do not exceed their upper version bounds. For an existing conflict, repair huggingface-hub in the virtual environment that backend uses, according to the common dependency range of the installed packages; do not upgrade the whole environment or change PyTorch/ROCm. After repairing, first verify `from transformers import CLIPTokenizer`, then restart the backend.

## Encoder errors during consecutive generations on Windows AMD

If the first image finishes and the next task fails in `TextEncodeQwenImage21` with `hipErrorInvalidValue`, and the background call stack is in `cast_to` / `copy_` of quantized weights, check the pinned memory compatibility of Windows ROCm rather than only whether the model files exist. In a two-round load verification of the Qwen quantized encoder, disabling only asynchronous offloading still failed, while disabling pinned memory made both positive and empty negative encoding pass. This project appends `--disable-pinned-memory` to the automatic startup arguments of local Windows AMD backends to avoid this pinned memory copy path; asynchronous offloading stays enabled, and transfer performance may vary by model and device. Administrators who enable `DisableInternalArgs` must set this argument themselves. The change takes effect after restarting the backend once the queue is idle; failed tasks are never retried automatically, and earlier successful results can be found in the personal history.
